# What a surface on this machine is

Fast, then simple, then visual, then controller-first, judged in that order. A
surface that is slow is already wrong, whatever else it gets right.

**Fast.** It is up, or it is not there yet. Nothing is animated into place and
nothing spins while it waits. What is known now is drawn now and the rest fills
in.

**Simple.** One subject per surface. A tab if there are several, a handful of
rows in each.

**Visual.** A colour, an icon, a bar, a picture. A word where none of those can
say it, and a sentence only when the word cannot.

**Controller-first.** The d-pad reaches everything on the surface. A takes it, B
leaves. Nothing waits for a pointer, and nothing is smaller than a thumb.
[`button-contract.md`](button-contract.md) is what each button owes;
[`panels.md`](panels.md) is how a surface keeps those promises.

## Not this

| Not | This |
| --- | --- |
| a desktop window, with a title bar and a corner to drag | a card the width of the screen, closed by B |
| a button the size of a word | a row the width of the card |
| a settings page of every control at once | a tab per subject, rows inside it |
| anything reachable only by pointer | the same thing on the d-pad |
| a paragraph | a name and its state |
| a question asked as rows in a list | its own surface: the question, then the answers side by side |
| a loading animation | the rows that are ready, and the others when they are |
| what a Linux desktop does because it has always done it | what a handheld does: full screen, few choices, big targets |

The last one is the one that goes wrong quietly. A menu that cascades, a dialog
that opens behind, a list that scrolls with a bar, a right-click that hides
half the actions: each is normal on a desktop and each of them is unreachable
or unreadable held in two hands at arm's length.
